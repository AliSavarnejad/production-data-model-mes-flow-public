# OPC UA to Database Mapping

## Purpose

This document explains how selected OPC UA-style machine signals can be mapped into structured SQL database tables.

The goal is to show the connection between automation-side data and database-side records in a simple IT/OT architecture.

This project does not implement a live OPC UA client. The mapping is conceptual and uses realistic example tags to show how machine data could be collected, normalized, and stored.

## Mapping Concept

A PLC or machine exposes operational data through tags or variables.

An IT/OT data collector or edge gateway reads selected values, adds context such as machine and production order information, and writes structured records into the production database.

## High-Level Mapping Flow

```text
PLC / Machine Signal
        ↓
OPC UA Node or Source Tag
        ↓
IT/OT Data Collector
        ↓
Mapping and Normalization Logic
        ↓
SQL Database Table and Column
```

## Source System Categories

The mapping separates different sources of information.

| Source system | Meaning |
|---|---|
| Engineering configuration | Static information defined during system setup |
| MES / ERP | Production order and product planning information |
| PLC / OPC UA | Live or sampled machine data |
| HMI / SCADA / System | Operator actions, alarm acknowledgement, system state changes |
| Database / Integration layer | Values generated or assigned by the data model or collector |

This distinction is important because not every database value comes directly from a PLC tag.

Some values come from engineering configuration, some from production planning, some from machine signals, and some from the integration layer.

## Why One Signal Can Map to Multiple Tables

Some machine signals can serve more than one purpose.

Example:

```text
Machine01.Alarms.ActiveAlarmCode
```

This signal is mapped to:

| Target | Reason |
|---|---|
| `machine_events.event_value` | Stores the alarm as part of the generic machine timeline |
| `alarm_events.alarm_code` | Stores the same alarm in a structured alarm lifecycle table |

This is intentional.

The generic timeline helps answer:

```text
What happened on the machine and when?
```

The structured alarm table helps answer:

```text
Which alarm occurred, how long did it last, and who acknowledged it?
```

## Machine Identifier Mapping

The project separates readable business identifiers from internal database keys.

Example:

```text
machine_id = M001
machines.id = internal database key
```

Operational tables do not store `machine_id` directly as the main relationship.

They store:

```text
machine_db_id
```

This makes the database relationship stable even if a display name or external identifier changes later.

## Production Order Context

Production order context is optional in operational tables.

This is important because not every industrial event belongs to an active production order.

Examples:

- machine setup
- test cycle
- maintenance event
- safety door opening
- automatic mode change before order start

For this reason, fields such as `order_db_id` can be NULL.

## Timestamp Handling

All timestamps are stored as UTC text values.

Example format:

```text
2026-06-01 08:30:00
```

SQLite does not enforce a strict datetime type in the same way as some other database systems. This project therefore uses a consistent timestamp format so that ordering and simple comparisons remain predictable.

## Example ALM-304 Mapping

The sample data includes a critical alarm scenario:

```text
Machine: M001
Order: ORD-2026-001
Alarm: ALM-304
Message: Jam detected at packaging station
Start: 2026-06-01 08:30:00
End: 2026-06-01 08:42:00
Acknowledged by: operator_01
```

The same scenario is represented across multiple tables:

| Table | Role in scenario |
|---|---|
| `machine_events` | Shows the fault in the machine timeline |
| `alarm_events` | Stores structured alarm lifecycle information |
| `cycle_records` | Shows a slower cycle before the fault |
| `energy_readings` | Shows higher power before the fault and lower power during idle/fault |
| `production_orders` | Connects the alarm to production order `ORD-2026-001` |
| `machines` | Connects all records to machine `M001` |

## Scope and Limitations

This mapping is intentionally simplified.

It does not include:

- live OPC UA browsing
- OPC UA security configuration
- OPC UA certificates
- automatic data collection code
- operator master data
- alarm text database import
- full MES integration
- historian integration
- real-time dashboard logic

The purpose is to demonstrate how selected machine signals can be modeled and explained in a database-oriented IT/OT portfolio project.
